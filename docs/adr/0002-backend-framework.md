# ADR-0002: 백엔드 프레임워크 FastAPI

> 상태: 제안 (docs/Architecture.md 초안과 함께 사용자 승인 대기, 패키지 설치 허용 확인 필요). 승인된 ADR은 수정하지 않는다 — 뒤집으려면 새 ADR로 대체.
> 날짜: 2026-11-06

## 맥락

- 백엔드 언어 Python 확정, 프레임워크는 사용자가 말하지 않음(PRD OQ 7 "프레임워크(예: FastAPI 등)와 단일/분리 구성은 사용자가 말하지 않음 — architect").
- 프론트(2명)와 백엔드(2명)가 동시에 일주일 안에 API를 맞춰야 한다 — 규격이 코드에서 자동으로 문서화되면 어긋남이 줄어든다.
- 서버 측 화면이 없다(React SPA — ADR-0003). 필요한 것은 JSON API, 입력 검증, 인증 의존성, DB 접근.
- 패키지 설치 허용 미확인(Architecture.md 실행환경 표).

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. FastAPI + Uvicorn | Pydantic 모델이 요청 검증·응답 DTO·OpenAPI 문서를 한 번에 제공(프론트–백엔드 계약). 의존성 주입(`Depends`)으로 인증·인가를 라우트마다 일관 적용. `TestClient`로 통합 테스트 간단. AI 모듈 DTO도 Pydantic이라 일관 | 관리자 화면·인증 기능 내장 없음 — 직접 구현(범위가 작아 감당 가능) |
| B. Django + Django REST Framework | ORM·마이그레이션·관리자 화면·인증 내장 | 설정·구조가 무거움, JSON API만 필요한 범위에 과함. AI 모듈 Pydantic DTO와 직렬화 계층이 이중화 |
| C. Flask | 가볍고 익숙한 경우가 많음 | 입력 검증·OpenAPI·DI를 확장 패키지로 조립해야 함 — 팀 내 방식이 갈릴 위험 |

## 결정

A(FastAPI)를 선택한다. 결정적 이유: Pydantic DTO가 곧 API 규격이자 OpenAPI 문서가 되어, 6인 팀이 Architecture.md의 DTO 표를 코드로 그대로 옮기고 프론트가 `/docs`로 확인할 수 있다.

세부: 엔드포인트는 동기 함수(`def`)로 작성하고 SQLAlchemy도 동기 세션을 쓴다(FastAPI가 스레드풀에서 실행). Gemini 호출도 동기 SDK 호출 + 타임아웃.

## 결과 (트레이드오프 포함)

- 얻는 것: 규격 자동 문서화, 라우트 단위 인가 의존성, 단순한 테스트.
- 감수하는 것: 비동기 대비 동시 처리량이 낮다 — 해커톤 시연 부하에서는 문제되지 않는다고 판단(추정 — 부하 측정 안 함). 관리자 화면 없음 — 시연 데이터는 스크립트로 적재(Architecture.md 배포 절).
- 설치 불허 시: Architecture.md "설치 불허 시 대안" 표 — 이 결정은 성립하지 않으므로 새 ADR 필요.
