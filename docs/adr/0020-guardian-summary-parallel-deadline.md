# ADR-0020: 보호자 학습 요약 — 영역별 AI 호출 병렬화 + 요약 전체 시간 상한

> 상태: 승인 (2026-11-15 사용자 승인 — 원문 "25초로 확정", 메인 세션이 사용자 지시로 기입). 승인된 ADR은 수정하지 않는다 — 뒤집으려면 새 ADR로 대체.
> 날짜: 2026-11-15
> 관련: DECISIONS #134. 바꾸는 범위는 DECISIONS #103(→ #114·#119 확정)의 **호출 방식(순차)과 시간 초과**뿐이다 — 호출 단위(영역마다 1회, 최대 3회)·요청 필드·`growth_level` null·검증(S1~S3)·"하나라도 실패하면 전체 `unavailable`"(#119 해석 6)은 그대로다. ADR-0017 본문은 수정하지 않았다. 구현 T-98.

## 맥락

- 팀원 리뷰 원문(PR #29, 사용자 전달 — 인용): "`app/services/guardian_report.py`에서 영역별 AI 요약을 순차적으로 호출하고 있어, 여러 영역의 응답이 지연되면 보호자 리포트 전체 응답 시간도 길어질 수 있습니다. 기본 AI 호출 타임아웃이 30초이므로, 3개 영역의 응답이 모두 느린 경우 요약 생성에만 최대 약 90초가 소요될 가능성이 있습니다. 단, 중간에 호출이 실패하면 남은 영역은 호출하지 않습니다." 권고 원문: "리포트 전체 AI 요약 생성 시간 제한 검토 / 영역별 AI 호출 병렬 처리 가능 여부 확인 / 응답 지연·타임아웃 회귀 테스트 추가 / 실제 Gemini 제공자를 통한 요약 API 연동 검증"

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 순차 유지 + 전체 상한만 | 동시성 없음, 변경 작음 | 진행 중인 동기 호출을 끊으려면 결국 실행기나 포트 변경이 필요. 영역 3개가 각 16초대면 48초라 상한에 자주 걸려 `unavailable`이 잦아짐 |
| B. 병렬만 (표준 라이브러리 스레드 실행기) | 최악 시간이 영역 수 × 30초 → 가장 느린 1개(≤ `AI_SERVICE_TIMEOUT_SECONDS`)로 줄어듦. 새 의존성 없음 | 상한이 `AI_SERVICE_TIMEOUT_SECONDS` 설정값에 묶임(설정을 늘리면 G3도 같이 늘어남). 연습 호출과 같은 값이라 요약만 짧게 할 수 없음 |
| C. 병렬 + 요약 전체 상한 (**선택**) | B의 이점 + G3 요약 대기의 최악값을 설정과 무관하게 고정. D-8의 "요약에 짧은 별도 시간 초과" 대응을 포트 변경 없이 실현 | 상한 초과 시 이미 보낸 호출은 끊을 수 없어 백그라운드에서 `AI_SERVICE_TIMEOUT_SECONDS`까지 돌고 결과는 버림(Gemini 사용량은 소모). 실패 시 "남은 영역 미호출"이 사라져 실패 경우 호출 수가 최대 2회 늘어남 |
| D. 비동기 전환 (`httpx.AsyncClient` + `asyncio.gather` + `async def` 엔드포인트) | 진행 중 호출 취소 가능, 스레드 없음 | DECISIONS #2·ADR-0002(동기 엔드포인트) 변경, 포트·HTTP 클라이언트·엔드포인트·Fake·테스트 전반 수정. 동기 SQLAlchemy 세션과 섞임 — 이 문제 크기에 비해 과함 |
| E. 포트에 호출별 시간 초과 인자 추가 (C와 결합해 남은 시간을 각 호출에 전달) | 상한 뒤 백그라운드 호출도 상한 근처에서 끝남 | `SummaryAI` 포트·`HttpPracticeAI`·Fake 시그니처 변경. 지금 측정된 문제(대기 시간)는 C만으로 해결됨 — 필요가 측정되면 새 결정 |
| F. 요약 저장(캐시) | 반복 조회 지연·사용량 감소 | 사용자 확정 비저장(DECISIONS #58)을 뒤집음 — 사용자 결정 사항, 이번 범위 아님 |

## 결정

C. 결정적 이유: 리뷰가 지적한 "영역 수 × 30초" 누적을 병렬로 없애고, 남는 최악값(호출 1개의 시간 초과)을 G3 전용 상한으로 고정하면서도 포트·의존성·동기 엔드포인트 결정(#2)을 바꾸지 않는다.

규칙(`GuardianReportService` 요약 부분 — T-98):

1. 입력 조립·기간·`insufficient` 판정(AI 미호출)은 그대로.
2. 영역별 `SummaryRequest` 조립은 그대로. 요청을 표준 라이브러리 `concurrent.futures.ThreadPoolExecutor`로 **동시에** 제출한다 — 실행기는 요약 1회마다 만들고 `max_workers` = 영역 수(≤3). 공유 실행기·새 의존성 없음. 워커 안에서는 `summary_ai.summary(request)` 호출만 한다(DB 접근 없음 — 저장소 조회는 제출 전에 요청 스레드에서 끝난다). 응답 검증(`accept_summary`)·항목 조립은 요청 스레드에서 한다.
3. 전체 상한 `SUMMARY_DEADLINE_SECONDS = 25`(app/services의 설정 상수 1곳 — 환경 변수 아님. 생성자 인자로 주입 가능하게 해 테스트에서 작은 값을 쓴다). 측정 기준은 첫 제출 직전부터의 단조 시계(`time.monotonic` 계열) — 기간 계산용 `clock`(UTC 날짜)을 쓰지 않는다.
4. 판정: 모든 영역이 상한 안에 응답하고 각 응답이 S1~S3 검증을 통과하면 `ok`, `items` 순서는 **입력 영역 순서**(완료 순서 아님). 어느 하나라도 `AIUnavailableError`·`summary: null`·검증 실패·**상한 초과**면 `status = "unavailable"`·`items` [](#119 해석 6 그대로 — 부분 결과 없음). 실패를 알게 되면 다른 영역을 기다리지 않고 바로 반환한다.
5. 반환할 때 실행기를 **기다리지 않고** 닫는다(`shutdown(wait=False, cancel_futures=True)`). `with ThreadPoolExecutor(...)` 블록은 빠져나갈 때 모든 호출을 기다려 상한을 무력화하므로 쓰지 않는다. 이미 보낸 호출은 끊을 수 없다 — `AI_SERVICE_TIMEOUT_SECONDS`까지 백그라운드에서 끝나고 결과·예외는 버린다.
6. `AIUnavailableError`가 아닌 예외(프로그래밍 오류)는 지금처럼 전파한다(→ 500 `INTERNAL`). 상한 초과 뒤 버려진 호출의 예외는 전파하지 않는다.
7. 로그: 상한 초과 시 warning 1줄 — 영역 수·상한값·경과 시간만(요청·응답 본문, 단서 이름 금지 — Architecture "로그" 행).
8. 공개 응답(`GuardianSummaryView`)·오류 코드·리포트 나머지 필드 변경 없음. 요약 실패여도 A11은 200.

상한값 25초의 근거: (가) 실측 영역 1개 리포트 16.6초(인용)를 `ok`로 통과시켜야 한다 — 그보다 짧으면 지금 동작하는 요약이 `unavailable`이 될 수 있다 (나) AI 쪽 Gemini 제한이 20초(인용, 504 관측)라 20초를 넘긴 호출은 AI가 이미 실패로 돌려주는 중이다 — 20초 + 네트워크·직렬화 여유를 둔다 (다) 백엔드 `AI_SERVICE_TIMEOUT_SECONDS` 30초보다 짧아야 상한이 의미가 있다. 값은 사용자 확인 대상(Architecture "설계가 올린 질문"이 아니라 이번 보고의 Open Question).

## 결과 (트레이드오프 포함)

- 얻는 것: G3 요약 대기의 최악값이 영역 수 × 30초(최대 약 90초 — 리뷰 원문)에서 25초로 고정된다. 영역 1개(현재)는 기존과 같은 1회 호출이며 최악값만 30초 → 25초로 줄어든다 — 지금 시연에서 체감 개선은 거의 없다(정상 응답 16.6초는 그대로, 추정 — T-98 ⑥에서 재측정).
- 감수하는 것: ① 상한 초과·첫 실패 뒤에도 이미 보낸 호출은 끝까지 돌아 Gemini 사용량을 쓴다(D-8). 실패 경우 호출 수가 "첫 실패까지"에서 "영역 수 전부"로 최대 2회 늘어난다. ② 요청 1건이 최대 3개의 추가 스레드를 쓰고, 상한 초과 시 그 스레드가 최대 `AI_SERVICE_TIMEOUT_SECONDS` 동안 남는다. 프로세스 종료 시 Python이 이 스레드를 기다려 종료가 그만큼 늦어질 수 있다(추정 — `concurrent.futures`의 종료 처리). ③ `httpx.Client` 하나를 여러 스레드가 동시에 쓴다 — 이미 FastAPI 스레드풀의 동시 요청이 같은 인스턴스를 공유하고 있어 새 종류의 동시성은 아니다. httpx 동기 클라이언트의 스레드 안전성은 문서로 재확인하지 않았다(추정 — 확인 방법: httpx 공식 문서 "Clients" 절, 또는 T-98에서 `HttpPracticeAI` + 모의 전송으로 동시 3호출 테스트).
- 바뀌지 않는 것: 영역마다 1회 호출(#114), 요청 필드·`growth_level` null(#103·#119 해석 5), 전체 실패 표시(#119 해석 6), 비저장(#58), 동기 엔드포인트(#2), 포트 시그니처.
- 측정 한계: 영역이 2개 이상인 실제 Gemini 실측은 출제 영역이 늘어난 뒤(T-30 이후)에만 가능하다 — 그 전까지 병렬 효과는 Fake 테스트로만 확인된다.
- 테스트(T-98 — architect가 정한 최소 케이스, 시간 제어는 실제 대기 대신 작은 주입 상한 + `threading.Event`/`threading.Barrier`를 쓰는 Fake 권고): Architecture "요약 실패 처리" 행의 2026-11-15 갱신과 이 보고의 목록을 따른다 — ① 동시 호출(Barrier — 순차면 실패) ② 입력 순서 유지 ③ 전체 상한 초과 → `unavailable`, 막힌 호출을 기다리지 않고 반환 ④ 일부만 초과해도 전체 `unavailable` ⑤ 한 영역 즉시 실패 → 상한 전에 반환 ⑥ 영역 1개 → 1회 호출 `ok` ⑦ `insufficient` → AI 미호출 ⑧ 기본 상한 = 25 ⑨ 비`AIUnavailableError` 예외 전파 ⑩ 통합: 상한 초과에도 A11 200·나머지 필드 정상 ⑪ T-76·전체 회귀 ⑫ 실제 Gemini 재측정(기준 16.6초와 나란히).
