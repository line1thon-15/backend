# ADR-0004: 인증·세션 — DB 저장 불투명 토큰 + httpOnly 쿠키 + 같은 출처 프록시

> 상태: 폐기(→ ADR-0013으로 대체, 2026-11-06 — 쿠키·토큰 방식은 ADR-0013이 이어받음. 프론트가 `VITE_API_URL` 절대 주소로 호출하는 실제 코드에 맞춰 같은 출처를 만드는 책임·요청 사항을 다시 정함. 승인 전 제안 상태에서 폐기). 승인된 ADR은 수정하지 않는다 — 뒤집으려면 새 ADR로 대체.
> 날짜: 2026-11-06

## 맥락

- F-01 "보호자 이메일 가입·로그인 … (인증 세부 방식은 설계에서 확정)", F-03 아이 로그인 "연결 코드 + PIN", F-04 재설정 후 "이전 값으로는 로그인 실패".
- 사용자가 둘(보호자·아이)이고 인가 경계가 핵심이다: 보호자는 자기 아이만(F-02 ④, F-30 ④, N-05).
- 이메일 인증 단계는 보류(PRD OQ 41).
- 프론트는 Vercel, 백엔드는 별도 PaaS(ADR-0007) — 출처가 다르다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 불투명 세션 토큰(DB에 해시 저장) + httpOnly 쿠키 + 프론트와 같은 출처(로컬: Vite 프록시, 운영: Vercel `/api` 리라이트) | 토큰이 JS에 노출되지 않음(XSS 시 탈취 어려움). 서버에서 즉시 폐기 가능(PIN 재설정 시 세션 폐기). `SameSite=Lax`로 CSRF 기본 방어. CORS 설정 불필요 | 매 요청 DB 조회 1회. Vercel 외부 리라이트의 쿠키 전달이 미검증(추정) — T-27에서 확인 필요 |
| B. 불투명 토큰 + 쿠키, 출처 분리(CORS `allow_credentials` + `SameSite=None; Secure`) | 프록시 불필요 | 서드파티 쿠키 차단 정책(Safari 등)에 영향받을 수 있음(추정). CSRF 방어를 별도로 해야 함 |
| C. JWT를 localStorage에 두고 `Authorization` 헤더 | 서버 무상태, 구현 예제 많음 | XSS 시 토큰 탈취, 즉시 폐기 어려움(F-04 재설정 후 기존 토큰 유효), 만료·갱신 로직 추가 |

## 결정

A를 선택한다. 결정적 이유: PIN 재설정·코드 재발급 시 기존 세션을 즉시 폐기할 수 있고, 아이·보호자 토큰이 브라우저 스크립트에 노출되지 않는다.

세부: 쿠키 이름 `sid`, `HttpOnly`, `SameSite=Lax`, `Path=/api`, 운영 `Secure`. 토큰 `secrets.token_urlsafe(32)`, DB에는 SHA-256 해시. 만료 7일(설정 상수). `auth_sessions.subject_type`으로 보호자·아이 구분, 역할이 다른 API 호출은 403. 상태 변경 요청은 `application/json`만 허용. 비밀번호·PIN은 Argon2id(DECISIONS #16).

## 결과 (트레이드오프 포함)

- 얻는 것: 단순한 인가 모델(세션 → 주체 → 소유 확인), 즉시 폐기, CORS 없음.
- 감수하는 것: 세션 테이블 조회 비용(시연 규모에서 무시 가능 — 추정). Vercel 리라이트 쿠키 동작이 실패하면 B로 전환하는 새 ADR이 필요(Architecture.md 설계 리스크 D-1).
- 알려진 한계: PIN 4자리 + 오류 횟수 제한 없음(F-44 보류) — Architecture.md [A-5].
